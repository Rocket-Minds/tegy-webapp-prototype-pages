## Corrected Product Understanding

The web app should wrap StrategyOS/Tegy behavior. It should not define a parallel backend model, and it should not force backend decisions from page structure.

The app concepts are UX projections, not MECE backend objects:

- Project: strategic matter / project context container.
- Vault: source inputs and context.
- Copilot: chat surface and routing entry point.
- Artifact: generated output produced by Tegy/StrategyOS.
- Decision Log: a view over decision points, locks, assumptions, and traces.
- Run/trace: visible progress from routing and agent work, not necessarily a persisted backend object.

These concepts may overlap in implementation. A single message can be a user prompt, a routing trigger, a decision request, a lock event, and the origin of an artifact. A decision can be modeled as a tagged message, `dp-index` entry, artifact frontmatter, separate record, or derived view; this must be resolved from the PRD and existing StrategyOS schemas.

The local Tegy plugin-pack review reinforces this correction. MECE is required for strategy decomposition and artifact scopes, but the app's page labels should not be mistaken for a MECE backend ontology.

## Do Not Bake Yet

These are open architecture decisions, not frontend-owned facts:

- Whether a decision is its own record, a tagged message, a `dp-index` entry, artifact frontmatter, or a derived view.
- Whether a message is the base event envelope for prompts, routing, decisions, locks, traces, and artifact triggers.
- Whether a run trace is canonical state, a streamed event, a UI convenience, a local StrategyOS log, or a derived artifact.
- Whether projects are app database records, StrategyOS project folders, hosted Tegy entities, or hybrid.
- Whether API commands call hosted Tegy, local StrategyOS, MCP, REST, or a generated skill wrapper.
- Which build/publish scripts should become production packaging primitives.

## First-Principles Architecture Questions

- What is the canonical state machine for a project from request to output?
- Which existing StrategyOS artifacts already own each state: `context.md`, `dp-index`, generated output files, chat-project instructions, hosted Tegy sessions, or something else?
- Which app views are projections over existing StrategyOS state?
- Which app concepts require new canonical storage?
- What must be deterministic, and what should remain orchestration-layer-dependent?
- What is the minimum API contract needed for Claude Code / Codex without baking the web app's internal model into the agent layer?
